# T37 refresh lifecycle inspection and correction

## Inspected baseline before changes

- AuthService generated an opaque UUIDv4 refresh secret, bcrypt-hashed it at cost 10 and stored only the hash in Redis at `refresh:<memberId>`, with a seven-day TTL. There was no database refresh/session table. One Redis slot per member meant a new login replaced that member's previous refresh session.
- The controller returned access JWTs in JSON and refresh secrets in HttpOnly, SameSite=Strict cookies, Secure in production, scoped to `/api/v1/auth/refresh`, with seven-day max age. RefreshDto required a UUID refreshToken even for cookie requests.
- Refresh expected separate member ID and secret arguments, but the controller incorrectly supplied refreshToken as the member ID. The service read the selected Redis hash, compared bcrypt, loaded the member, deleted the hash and called token issuance to SET a replacement.
- GET/compare/DEL/SET were separate operations: two concurrent requests could verify the same old hash and independently issue credentials. Logout/password reset deleting the key during a refresh could also be followed by an unconditional SET that resurrected the refresh session.
- A wrong secret deleted the selected member's refresh slot, letting an unauthenticated caller with a member locator revoke another member's session. Login and refresh always minted the member role. Access JWTs expired after 15 minutes; Redis refresh TTL and cookie max age expired after seven days and renewed on rotation.
- Logout deleted the member's Redis slot and cleared the cookie. Password reset deleted the slot after the database password update. Neither mechanism invalidated already issued access JWTs. Existing reset-token consumption and refresh-login races had no cross-system transaction.

## Selected correction within the existing storage model

Retain the opaque UUID secret, bcrypt hash, one Redis slot per member and existing lifetimes. A validated memberId is only a locator. Authenticate the secret against that slot before looking up the member or issuing credentials. Invalid secret/absent slot responses are generic 401; invalid attempts do not delete someone else's slot.

Prepare a new secret/hash and access JWT, then atomically compare-and-swap the old exact Redis hash to the new hash with renewed TTL in a single Lua operation. Return credentials only to the successful CAS caller. A concurrent rotation, logout, reset or login that changed/deleted the old hash makes CAS fail; no unconditional refresh SET can resurrect it. This needs no new session table or broader session architecture.

Login and refresh derive member/admin claims from current database authority; JWT validation independently reloads authority on every authenticated request. There is no role input from clients. Role revocation therefore does not depend on refresh-token rotation or access-token expiry.

Implementation and executed test evidence are recorded below; final check counts are in T37-governance-checkpoint.md.

## Implemented lifecycle

- RefreshDto now requires a separate bounded memberId locator and permits an optional UUIDv4 body secret. The HttpOnly cookie takes precedence. A member locator is never treated as authenticated identity. Missing, expired, wrong, cross-member and replayed secrets receive the same generic service-level 401. Missing slots perform dummy bcrypt work to reduce a session-existence timing difference; no perfect constant-time network behavior is claimed.
- Redis still stores only the bcrypt hash. Secrets are UUIDv4 values generated by Node crypto.randomUUID. Hashing cost remains 10, refresh TTL remains seven days, and access JWT expiry remains 15 minutes. There is no new session table, session index or multi-device redesign.
- Refresh compares the presented secret with the selected hash before loading member identity or authority. It prepares replacement credentials internally, then uses Redis Lua to compare the exact old hash and SET the replacement with EX in one atomic operation. Credentials are returned only if that CAS succeeds. Failed CAS returns generic 401; it never SETs or deletes a winner's replacement.
- Concurrent refreshes may both prove the old secret, but only one can replace the old hash. Old secrets cannot match the new salted hash, so replay fails. An invalid cross-member secret cannot match the other member's bcrypt hash and does not delete either slot. A missing, unverified, suspended or closed member with a proven secret is rejected and its slot is deleted only if it still equals the proven hash.
- Login reloads trusted email verification, membership status and isAdmin before issuing tokens. Refresh loads the same state after verifying possession. Neither operation accepts a role from a request or old JWT.
- JWT verification retains signature and expiration checks, reloads current member state and rejects absent/suspended/closed members. Admin authority comes only from isAdmin, overriding a stale signed admin claim. Existing signed staff/compliance/board claims retain their prior handling; their provisioning/policies were not redesigned. Login/refresh still issue only member or admin. No ordinary member API can change isAdmin.
- Logout and password reset retain their Redis deletion behavior. If deletion happens before a pending refresh's CAS, that refresh cannot recreate the session. If CAS happens first, subsequent deletion removes its replacement. New login remains a deliberate new session that replaces the single per-member slot.

## Request contract

Cookie client:

```http
POST /api/v1/auth/refresh
Content-Type: application/json
Cookie: refresh_token=<opaque-secret>

{"memberId":"<member-id>"}
```

The body fallback is `{ "memberId": "<member-id>", "refreshToken": "<opaque-UUIDv4-secret>" }`. Roles and other undeclared fields are rejected. The response contains the accessToken; a rotated refresh secret is set only through the existing cookie response. Clients must supply memberId separately; they may obtain this locator from their login JWT's sub, but the locator itself proves nothing. The former broken refreshToken-as-memberId contract is intentionally not retained.

## Evidence and practical limits

Actual tests use real PostgreSQL, Redis, bcrypt, local/JWT guards and cookie parsing. They verify cookie/body rotation, stored hashing and TTL, invalid/cross-member rejection, concurrent CAS arbitration, replay rejection, promotion/demotion at login and refresh, logout interleaving, password-reset deletion, expiry, inactive/unverified members, and client self-promotion rejection. Only the external HIBP lookup is stubbed for the reset test; rate-limit quotas are bypassed in this focused suite, while authentication guards remain real. Unit tests also verify that invalid secrets trigger no member lookup and authority lookup failures do not return credentials. Final verification passed 22 unit tests and 44 integration tests; a full --detectOpenHandles run with a 30-second command-line timeout also passed all 44 tests with no open handles reported. Earlier timeout failures and their resolution are recorded in the main T37 report.

Security limits retained from the existing architecture:

- One refresh slot per member; new login replaces the prior refresh session. There is no multi-device session inventory or session-family replay detection. Replaying an old secret is rejected but does not revoke a valid replacement, which also prevents an attacker from revoking someone else's session with an invalid secret.
- Logout/password reset revoke refresh state, not already issued access JWTs. Such JWTs retain their 15-minute lifetime, subject to current database member status and immediate current admin authority checks. This work does not claim general immediate access-token session revocation.
- Redis CAS governs refresh serialization on the serving Redis primary; Redis persistence/failover configuration is outside this change. Restoring stale Redis data can restore stale session state. A lost response after successful rotation requires login again because the client may not receive its replacement secret.
- Database authority and Redis session state have no cross-system transaction. Authority can change while credentials are being prepared; every later authenticated request reloads it. Already running transactions can serialize before a concurrent authority revocation; this change does not cancel in-flight work.
- Existing password-reset token consumption, refresh-cookie path/protection, and new-login/password-reset races are not redesigned. Access-token theft, signing-key compromise and privileged database writes remain security boundaries. No administrator was provisioned and no operational grant/revoke command was executed.
